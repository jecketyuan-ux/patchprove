# patchprove 2.0 发布修复与 2.x 升级优化方案

日期：2026-10-22（UTC）。依据：[代码审查 R01—R07、D01、L01—L04](01-code-audit.md)、[模块/数据/竞品评审](02-product-modules.md)。代码基线 `6fa50972f424ee0b6c8e2b1a8506b7ee3f804f0d`，与已合并 main 的 tree 相同。本文是可审阅的后续实施方案；本轮仅交付审查与复现材料，未实施这些产品修复。

## 1. 升级目标与决策

**先使严格模式的成功结论可信，再扩大支持范围。** 当前 2.0 已合并并通过对应远程 CI，但有新确认的错误放行反例，不建议直接发布现有候选。后续候选应修复反例、重新验收，并明确哪些宿主/上游版本进入稳定支持范围。

保留 Node/TypeScript、CLI/SDK/MCP、无模型主判定、无默认遥测、无服务依赖的定位。成熟度以验证事实与结论是否一致、异常是否有界、交付是否可复核衡量，不以更多开关、语言或集成徽章衡量。

以下六项作为长期不变量：

1. 分析与执行对应同一明确代码快照；发生漂移时不得给出完整通过。
2. 计划、收集、实际执行、跳过和未知范围可分别追溯；一个成功单元不能替缺失单元作证。
3. 不能解析的相关内部依赖触发保守回退或不完整，而非静默缩小选择集。
4. 一份证据中同一执行身份只有一个事实；结构、语义、摘要、判定一致。
5. 完整性、签名有效性、可信来源与执行语义分别报告；入口不得静默忽略调用者要求。
6. 当前支持声明必须指向候选 SHA/tree、真实环境与验收记录；历史绿灯不能移给行为已改变的新提交。

## 3. 第一阶段：修复验证事实与判定链

### U01：从 runner 结果重建实际执行集合

不要把 `argv` 中的路径复制到 passed record。由执行单元描述生成请求计划，runner adapter 返回可验证的本次结果，再由统一核账器计算缺失范围。

```text
requested scope
  → runner invocation
  → fresh machine report + report digest
  → collected / executed / skipped / failed / unknown
  → required-scope reconciliation
  → passed | failed | incomplete
```

首批可采用：Vitest/Jest 受支持版本的 JSON/reporter 数据；pytest 的机器报告/插件接口；Go `-json` 的 package/Test 事件与文件映射；Cargo 的可稳定使用接口或明确保持 crate 粒度；Java 沿用本次新鲜 XML 并补 skipped/failed 明细。选择接口前核实版本稳定性，不能依赖不受支持的 nightly 输出却声称普遍可用。

每种语言定义最小可承诺粒度。不能可靠获得文件级执行证据的 runner，可以证明整个项目/crate 的执行范围，但必须解释其与计划的关系；没有依据时返回 unknown。将 collected、executed、passed、skipped 分开，不使用单一计数同时表达这四件事。

验收必须包含本轮排除和全 skip 反例；对照保持全量正常时可通过。加入多文件只有部分执行、部分项目缺报告、reporter 崩溃、陈旧报告、参数过滤、zero collection、输出截断、JUnit/Surefire 多 suite、混合语言单侧缺 runner。每个错误样例先在当前基线复现，修复后以健康行为建立正式回归。

### U02：先分类未知依赖，再决定回退范围

建立解析结果类型，区分 built-in、外部包、仓库内部已解析、仓库内部未解析、动态表达式。package imports 按最近 package scope 处理条件/通配；解析配置和版本进入 provenance。对无法解析的相关内部依赖，使用最小可靠项目边界回退；项目边界本身不可靠时扩大到语言/仓库，或给出阻止严格通过的缺口。

避免两个极端：所有 unknown 都当无影响，或所有 `node:`/外部包 import 都触发全仓回退。前者漏选，后者会让正常项目几乎总是全量。使用 Nx/Turbo 的导出项目图可帮助限定范围，但不在此阶段要求用户采用它们。

验收包含 R02 原样、相对导入对照、nested package、条件 imports、通配符、配置损坏、未安装外部包、内置模块、删除前图和锁文件变化。数据组合应满足可测试的单调性：增加普通覆盖数据不能删除已知依赖边；解析能力降低时不能无解释地缩小需要验证的范围。

### U03—U05：协议与入口统一约束

执行事实只维护一份内部模型。兼容期 `checks[].records` 与顶层记录由同一模型投影，reader 拒绝副本不一致；长期删字段只能在明确的新协议主版本完成。校验不仅检查类型，还检查身份/引用、检查与单元归属、计划覆盖、状态与退出码/计数、摘要和存储 decision。

adapter 在任何成功推导前验证状态、字段类型和冲突，单份输入失败不留下部分记录。`plan`、`cache`、`imported execution`、`local execution` 有独立含义，不能通过 `exit0` 自动跨越。新 reader 要明确支持的 adapter/version，而不是依赖“看起来像 Nx JSON”。

对所有入口采用同一参数归一化/组合校验。sign-only 的可选设计有两种：默认创建 receipt，或报“签名需要 receipt 输出”的明确错误；推荐沿用用户显式 sign 意图生成 receipt，并拒绝与 `receipt:false` 冲突。缺 key 在执行昂贵检查前尽早报错，但不要把 key 传入测试进程或记录到证据。

## 4. 第二阶段：完成发布前真实验收

### 4.1 候选与证据账本

新增候选索引，推荐目录 `docs/validation/release/<candidate-sha>/`，不要覆盖现有历史 JSON。索引至少记录 candidate SHA/tree、PR、CI run/attempt、job、OS/Node/runner、命令、结果、artifact/tarball 摘要、源数据链接和边界。R07 可先利用本报告保存的远程元数据补档；修复产生新代码后必须记录新的候选验证。

账本应同时容纳 passed、failed、incomplete、not-run，不能用一个勾选框抹去未完成项。自动生成支持矩阵时，使用版本化规则和明确有效候选；时间戳只表示运行时间，不证明与代码匹配。

### 4.2 依赖处置

将 10 个唯一 GHSA 按包版本和前置条件逐项归档，优先处理实际使用的 worker/转译链和可暴露服务入口。选择上游明确修复的版本集合，先迁移测试配置/reporter，再重跑 U01 的机器报告合同与现有回归。

验收保留 `npm audit --omit=dev` 与完整审计两份结果，口径分别为受影响包数和公告数。无修复版本/不可达项要有理由、责任人、到期复查条件；不能写作“因为是 devDependency 所以无风险”。对锁文件强制覆盖的依赖做接口验证，避免安全升级破坏实际执行记录解析。

### 4.3 原始生产链和真实宿主

在独立消费项目中安装最终 tarball，使用原始 detectTools、插件和 CLI 调用每种语言 runner；保留原生 harness 作为较快的执行器测试，两者不能互相替代。gitleaks 使用固定版本及摘要验证混合暂存、未暂存、未跟踪、忽略、范围与扫描失败，同内建扫描比较输入范围。

Claude Code 与 Cursor 各固定实际版本和平台，执行通过/失败/不完整、取消慢检查、重复 stop、loop limit、多 workspace、含空格/非 ASCII 路径、配置合并和实际 MCP 启动。Claude 阻断与 Cursor 建议分别验收；不要为了同一产品词汇而伪造两者能力相同。

不能运行的宿主标为尚未验证；若必须发布核心 CLI，可明确保持该宿主集成为实验性并给安装/回退说明。不能将协议 stdin 替身结果勾成宿主端验收成功。

### 4.4 GitHub publisher

读写权限分离保持不变；artifact 不执行脚本，Markdown 由可信代码生成。新增 head/run/attempt 关联与 PR 当前 head 复核，配合按 PR 的并发控制。旧事件应留下可追踪的 skip 原因，不能覆盖当前评论。

在同仓库和 fork 的最小验收 PR 分别运行通过/失败/不完整、缺 artifact、错误 hash/head、取消、旧成功晚到、新失败先到、分页与同 marker 不同作者、权限不足。记录实际 run/artifact/comment URL。发布成功不能改变原验证失败退出码；没有稳定 PR 关联的事件应明确跳过，不能猜测目标 PR。

这些外部写操作属于未来实施时的明确任务，本轮审查不执行。发布 npm/tag/release 仍需要单独明确操作目标；候选和发布材料必须先准备成可审阅结果。

## 5. 第三阶段：2.x 成熟度建设

### 5.1 资源与环境

对文件大小、总输入字节、文件数、JSON 深度/规模、解析与压缩阶段设预算；尽量流式哈希，避免同一大文件多份 Buffer 和同步阻塞。取消应贯穿 Git、采集、解析、工具、产物，不只杀子进程。基准必须固定文件大小和硬件，测峰值 RSS/CPU、阶段耗时与取消延迟，再确定默认值。

环境记录只采集必要且非敏感的信息：OS/架构、Node/runner 版本、工具可执行来源或摘要、依赖锁摘要、关键显式配置。不要记录全部环境变量，不为追溯而泄漏密钥。外部数据未纳入身份时明确列出，保持“未密封”标签；容器/沙箱可作为调用者能力，非此轮强制重建的平台。

### 5.2 项目级计划与插件契约

用单一 `ExecutionUnit` 描述产生计划、执行和结果，消除 planFor/gates 双份注册。每项目表达适用性、required/optional、不适用理由、runner、工作目录、配置来源及范围。

新插件/adapter 必须提供能力声明、受支持工具版本、计划粒度、机器结果解析和 incomplete 语义；供应的实际执行记录不能绕过统一语义校验。保留显式本地插件授权；插件信任与 OS 隔离不是同一个开关。

首批真实上游接入只选择有用户价值且有稳定机器接口的场景：Nx/Turbo 计划/任务结果、testmon 来源明确的历史依赖、reviewdog/SARIF 消费。Cosign 已有有限 wrapper，优先维护受测版本与信任材料，不建设自己的透明日志或身份基础设施。StrykerJS 等质量报告可先作为可选导入，单独表达断言质量，不影响默认执行预算。

### 5.3 真实项目语料与维护者体验

按模块缺口挑选真实项目，优先 package imports、多配置 monorepo、pytest deselection、Go build tags/workspace、Rust cfg/ignored tests、Java 多模块任务。记录许可证与固定 base/patch；先确认基线，再运行选集/全量，人工标注因果。

仪表数据采用本地/CI artifact，项目不自动回传。每次运行可给维护者简短解释：因何选择/回退、哪些要求已执行、哪些缺证据、如何补齐。输出应将问题定位到项目/文件/单元/原因，并给出可安全重放的命令，不把实现细节塞给普通使用者。

等可靠性与实际成本被测量后，再考虑缓存或增量持久化。缓存键至少绑定快照、策略、工具/解析器、相关环境；历史复用必须标 cached/imported，不能重写成 local execution。

## 6. 协议、版本与迁移

当前 package `2.0.0` 尚未正式发布。应在发布前修正明确 bug；若相同版本制品已经被外部使用，应分配新的候选/补丁版本和摘要，不能覆盖同版本产物造成不可追溯。最终版本命名由实际 registry/tag 状态核实后确定，不在本报告凭假设创建版本。

| 变化类型 | 处理方式 | 迁移验收 |
| --- | --- | --- |
| 错误放行修复 | 保留三态和接口，过去 passed 可能变 failed/incomplete；发布说明给具体反例 | 正常已满足范围仍通过；新增拒绝有真实原因，不靠 `--no-strict` 掩盖实际失败 |
| 新增可选执行/解析来源字段 | 2.x 增量协议；reader 忽略未知可选字段但验证已知字段 | 新旧消费者对已知事实一致；字段缺失不得伪造为已执行 |
| 收紧畸形输入读取 | 明确 JSON pointer 和错误代码，不修复/重签恶意或矛盾输入 | 旧合法包能读，R03/R04 非法包拒绝；历史版本按其真实语义处理 |
| 移除重复字段、改变已有必需语义 | 后续协议主版本，先提供转换和弃用窗口 | 不把旧 receipt 重新解释为新版签名；转换保留来源与 legacy/incomplete |
| 支持矩阵收缩/实验性标记 | 发布说明、初始化模板、README 和 RoadMap 同步 | 用户能识别稳定与待验能力，安装配置固定包/工具/宿主版本 |

灰度阶段可保存旧/新判定及差异原因，让维护者识别新增暴露的真实缺口。只在用户明确配置时容许兼容边界，不默认接受缺执行事实；回退到旧版本应固定版本和产物，不改变已发布签名含义。

## 7. 发布验收与停线条件

| 验收项 | 必需证据 | 拒绝放行条件 |
| --- | --- | --- |
| 已确认反例 | R01—R06 的原样复现、健康预期回归和合法对照 | 仍将未执行/漏选范围判 passed，或输入契约继续静默接受 |
| 代码/策略身份 | 混合暂存、特殊路径、测试变更、删除、range/工作区不一致、执行漂移 | 身份丢失/漂移却通过；已修旧反例回归 |
| 执行事实 | 五类语言的真实结果核账、缺工具、零执行、skip、排除、超时/取消 | 请求范围直接当实际执行；任何必需 unknown 被成功单元掩盖 |
| 协议与签名 | reader 语义一致性、合法历史兼容、未知 major、篡改/缺签名/不可信 signer | 不一致 evidence 被通过；信任或 signature 被混同 checksum |
| 入口/包 | CLI/SDK/MCP/钩子/Action 参数及决策矩阵，最终 tarball 消费端 | 同证据结论不一致；签名要求无响应；初始化入口无法使用 |
| 平台/工具链 | 新候选的 Node 22/24 ×三 OS、真实 runner、Go launcher、受支持扫描器 | cancelled/skipped/未触发被算 success；旧 head 结果借给新代码 |
| 真实宿主/发布反馈 | 精确版本、项目、事件、run/artifact/comment 或交互记录 | 稳定支持声明没有实际验收；旧 run 覆盖新状态 |
| 依赖/文档 | 两种依赖审计、逐项处置，候选账本、迁移/支持说明 | 可达风险无处置；当前支持声明与记录矛盾 |
| 效果宣称 | 固定真实语料、人工归因、分母/unknown/缓存环境 | 宣传零漏检或性能倍率，却只有种子样例或营销资料 |

发布出口是一次明确候选的审阅结果，不是“仓库某次 CI 变绿”。修复后无需无目的重复所有测试；按变更影响运行必要检查，并完成上述已定义的发布门槛。每个失败需关联修复提交和新结果，不能以重复重跑隐藏 flaky 或环境错误。

## 8. 暂缓投入与重新评估条件

| 暂缓方向 | 原因 | 何时重新评估 |
| --- | --- | --- |
| SaaS、多租户、计费、中心化遥测 | 与当前明确定位和已证实问题无直接关系 | 多个真实用户提出托管需求，且数据边界/运营成本有依据 |
| LLM 主判定/通用自动代码审查 | 不解决当前执行证据问题，改变确定性产品承诺 | 作为可选外部报告导入且不参与必需确定性结论时再讨论 |
| 重写 Go/Rust 内核、单二进制替代 | 当前缺陷主要在模型/语义，换语言不会自动修复 | 安装/运行时成本有真实测量并超过维护双栈成本 |
| 自建全生态编译/项目图 | 维护成本高，成熟工具已有深度 | 特定高价值场景无法通过稳定机器接口接入时 |
| 广泛结果缓存/极限性能优化 | 可能放大当前身份与执行粒度错误 | U01—U04 稳定且真实基准指出明确瓶颈后 |
| 新增大量语言和集成徽章 | 容易重复“有插件但缺真实验收” | 新语言有维护者、固定工具版本、真实项目和异常矩阵时 |

完成本方案的标准是：维护者能从候选和证据回答“验证了什么、没验证什么、为何给出这个结论”，并且已知反例无法再得到错误成功。扩大生态的每一步都应增加可验证的用户收益，而非扩大未经证实的承诺。
