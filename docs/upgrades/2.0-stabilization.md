## Executable release gate

`npm run check:acceptance -- --ledger /path/acceptance.json --tarball /path/patchprove.tgz` verifies:

- Exact source commit/tree, built runtime digest and actual tarball SHA-256. Packaged executable/schema/package bytes must match the measured build; compressed and expanded archives are bounded and never extracted or executed. The source checkout must be clean.
- All twelve required current-head CI jobs completed successfully in the recorded run and attempt. Skipped/cancelled/pending jobs do not count.
- Forty-four live cases: nine scenarios each in Claude Code and Cursor, eleven scenarios each on same-repository and fork GitHub PRs, and four Windows production groups.
- Each record's candidate identity, real tool/host versions, observed behavior and bounded raw-log bytes/digest. Logs remain inside the evidence directory and are never executed.
- Attributed assertions in Windows negative cases, all thirty native scenarios, actual PR comment/run references, unchanged verification exits, cancellation cleanup and host-specific blocking/advisory behavior.

The gate exits 1 for missing, invalid, failed, incomplete or not-run acceptance. It exits 2 for unreadable/invalid CLI input. `--matrix` renders the same checks as Markdown and keeps the failure exit. `--template --tarball FILE` emits an initial **not-run** ledger; it does not run hosts or invent observations. The validator checks recorded consistency and raw bytes, not producer honesty or cryptographic identity. Independent review of the source runs remains necessary.

The read-only `Release acceptance` workflow checks an uploaded `release-acceptance` artifact containing `acceptance.json`, `patchprove.tgz` and relative log files. It checks out the selected candidate, downloads evidence into runner temporary storage and runs trusted validation code. It has no npm, tag or release publication step. Creating a passing ledger or adding this workflow does not authorize publication.

## Windows investigation

Retain success, actual assertion failure and multi-module fixtures under the original path conditions. Both native and installed fixture directories include Chinese characters and a space. The Java negative controls require an actual JUnit assertion failure; class-loading errors, `<error>` nodes and unknown failure types cannot satisfy them. Probe the actual selected launcher for JDK/Gradle, `native.encoding` and `file.encoding`; retain independently observed classpath/worker information where available. A launcher observation must not be relabeled as proof of a daemon/test-worker JVM, and unavailable worker identity remains unknown. Do not store complete environment variables or JVM secret options. Gradle [#30304](https://github.com/gradle/gradle/issues/30304) addresses argument-file encoding; [#30391](https://github.com/gradle/gradle/issues/30391) concerns characters unrepresentable in system encoding. The latter remains open in the checked upstream record. Raising supported tool minimums is allowed, but neither version changes nor a UTF-8 declaration count as a demonstrated fix.

No failed path case is removed to make CI green. If no tested tool combination passes, release remains blocked. Current support documentation must say failed/not-run until actual results exist.

## Candidate evidence and packaging

Keep raw acceptance evidence outside the tracked source checkout or in ignored caller-owned storage. Raw archives under `docs/validation/` remain in Git for historical review but are excluded from the ordinary npm tarball together with local review materials. Current migration/support instructions remain packaged.

When `PATCHPROVE_PACKAGE_REPORT` is set, the installed-package harness retains the exact tested tarball, its digest, command logs and the valid smoke-test evidence/report bundle beside the report. It also writes failure status before removing temporary consumers. Every CI package job enables this retention and uploads its evidence even on failure. The retained tarball's executable/schema/package bytes are compared to the measured local build before installation.

The first real-project corpus remains five pinned projects, five language families and ten controlled patches. A new run must retain independent baseline/full truth and selected outcomes, source/license identity, unknown denominators, missed/extra selection, blocked neutral changes and timings. Old digests establish old bytes, not a new measurement. Ten projects/fifty historical patches are a later expansion; no population zero-miss or generic speedup claim is made.
